# 模块设计文档：目录规则

本目录放**逐模块**的设计文档：**一个模块一个文件**，一份文档只写一个模块，**动手实现之前先写它**（[../../CONTRIBUTING.md](../../CONTRIBUTING.md) 硬规定 4）。

> 这份 README 只是规则与模板，**它不是写设计的地方**。不要把多个模块的设计堆进任何一份共用文件；每个模块的设计写在 `docs/design/<模块名>.md` 里——`packages/host` 就写 `docs/design/host.md`。

## 它不重复什么

| 文档 | 回答的问题 |
|---|---|
| [../kernel.md](../kernel.md) | 内核承诺什么 |
| [../implementation.md](../implementation.md) | 用什么做（选型，以及已核查过的依赖事实） |
| [../plan.md](../plan.md) | 先做什么（批次、依赖、验收标准） |
| 本目录 | **这个模块具体怎么做**：接口、数据流、失败路径、用哪些测试验收 |

本目录不重新定义语义：接口的含义仍以 kernel.md 为准，选型仍以 implementation.md 为准。两者有冲突时，冲突写进设计文档并给结论，收尾时回写 implementation.md 的事实表 / 风险表（plan.md 第 0 节）。

## 什么时候写

- 实现一个新模块之前：先给它单独建一个文件，写完这份文档再动手
- 改动既有模块之前，只要改动越过"实现细节"：对外接口变了、关键数据流变了、失败路径变了——改的还是**这个模块自己那份**文档
- 模块实现完之后：把实际结论回写进文档，状态改成"已实现"

## 命名：一个模块一个文件

文件名就是模块名，不带 scope 前缀；**一个模块一个文件，模块之间不合并**（`core` 与 `host` 不许写成同一份）：

| 模块 | 文档 | 现在有没有 |
|---|---|---|
| `packages/core` | [core.md](./core.md) | 有（实现后补写） |
| `packages/eslint-config` | [eslint-config.md](./eslint-config.md) | 有（实现后补写） |
| `packages/host` | `host.md` | 没有——动手前建 |
| `packages/kit` | `kit.md` | 没有——动手前建 |
| `crates/plugin-host` | `plugin-host.md` | 没有——动手前建 |
| `crates/tauri-plugin-cambia` | `tauri-plugin-cambia.md` | 没有——动手前建 |
| `spec/` | `spec.md` | 没有——动手前建 |

## 必备内容

1. **边界**：负责什么；明确不负责什么，不负责的部分指向谁
2. **接口**：对外的 API / 命令 / 协议（签名或字段表），以及兼容性承诺
3. **数据流与状态**：关键流程怎么走、状态存在哪、谁在什么时候改它
4. **失败路径**：出错、超时、崩溃、重复调用分别是什么行为；错误码从哪来（JS 与 Rust 共用的错误码表在这一节对齐）
5. **验收方式**：哪些测试证明它成立，对应 plan.md 里那一批的验收标准
6. **未决项**：还没定的，以及打算怎么定（批内验证 / 实测 / 时间触发）
